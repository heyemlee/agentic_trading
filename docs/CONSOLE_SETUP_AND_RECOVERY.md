# 控制台登录与订单恢复

控制台的登录、会话、审批、订单恢复、备份与通知。launchd 部署与手机访问见 [MACOS_DEPLOYMENT.md](MACOS_DEPLOYMENT.md)，实盘开关见 [OPERATIONS.md](OPERATIONS.md) 的 Real money 一节。

## 首次使用

在项目目录执行：

```bash
uv sync --frozen
uv run ct-auth
uv run ct-api
```

`ct-auth` 会在终端安全提示输入密码，两次一致才保存。默认用户名为 `owner`。密码有两条路径，任选其一：**16 个字符及以上**只看长度，不再要求字符种类（长口令就是靠长度）；**8–15 个字符**则必须同时包含大写字母、小写字母、数字和特殊符号，缺一类会被拒绝。短于 8 位一律拒绝。配合登录限速（5 分钟内 5 次失败即锁），短密码面对的是离线破解而不是在线猜测。打开 `http://127.0.0.1:8787/ui/` 登录。

密码以 scrypt 加盐哈希写入 `state/console_auth.json`，文件权限必须为 `0600`，且已加入 Git 忽略规则。可通过 `CT_AUTH_FILE` 更改位置。重复运行 `ct-auth` 可以轮换密码，现有会话会在下一次请求时失效。不要把密码放进命令行参数、前端源码或聊天。

会话使用 HttpOnly、SameSite=Strict Cookie；通过 HTTPS 时 Cookie 带 Secure。浏览器和服务端会话最长 30 天，API 重启后仍有效。SQLite 只保存会话令牌的 SHA-256 哈希；退出登录、密码轮换或到期会撤销会话。失败登录每 5 分钟最多 5 次；限流保存在单个进程内，因此当前部署必须使用 **单 worker**。手机丢失时，应从 Tailscale 撤销该设备并轮换控制台密码。

## 访问边界与手机

默认仅接受 `http://127.0.0.1:8787` 和 `http://localhost:8787`。业务数据接口、控制操作、研究记录与 API 文档均需登录。未配置密码时业务接口拒绝访问。所有写请求必须来自允许的 Origin，使用 JSON、`X-CT-Request: 1` 和会话 CSRF token；外部身份请求头不被信任。

手机不能直接访问电脑上的 `127.0.0.1`，要经过私有网络入口或 HTTPS 反向代理；本部署使用 Tailscale Serve，步骤见 [MACOS_DEPLOYMENT.md](MACOS_DEPLOYMENT.md) 的 Private phone access。准备好自己的 HTTPS 域名后，将其精确设置在 `CT_ALLOWED_ORIGINS`；多个域名用逗号分隔。非本机 HTTP 地址会被拒绝。后端保持监听 loopback，只信任你控制的本机代理来传递 HTTPS 协议信息；不要把代理信任范围设为所有来源。前端与 API 必须同源。

## 审批规则

服务端要求明确的 `confirm: true`、完整提案 ID、版本、ticker、bucket、action、金额及卖出数量，并要求每次确认带 UUID 幂等键。审批人来自登录会话。版本或条件不匹配返回冲突；同一请求重试返回原结果，不会再次下单。

弹窗冻结打开时的对象。队列刷新或关键数据过期会禁用确认。请求超时后到 Activity 查询订单，避免靠重复批准猜测执行情况。

`SELL` 默认卖出该桶中的全部持仓；`REDUCE` 默认减半。股数在研究阶段确定并保存，在审批时按最新持仓核对，向下截断至六位小数，不会超过持仓。小额尾仓允许卖出；不能表示为有效股数时拒绝执行。旧的零金额 SELL/REDUCE 提案需要重新研究，不能猜测用户批准了多少。

## 订单恢复与对账

提交前先保存订单意图和 client order ID。返回券商 ID 后立即保存，再同步成交。状态包括 SUBMITTING、SUBMITTED、PARTIALLY_FILLED、EXECUTED、CANCELED、UNKNOWN。只有券商报告最终成交并完成本地记账后才显示 EXECUTED。

后端启动后及每轮同步完成约 15 秒后，会查询已有订单。暂停交易或关闭实盘开关不会停止这些只读券商查询。也可运行：

```bash
uv run ct-reconcile           # 同步一次
uv run ct-reconcile --watch   # 持续同步
```

恢复器只查询已有订单，不新下单、不取消订单、不重做券商预审。API 已运行时通常不需要额外运行恢复器。

每个订单的累计成交游标、增量事件、现金、持仓、提案状态和成交审计保存在同一次 SQLite 事务中。任何一步失败都会整体回滚，恢复器随后按券商的累计成交重新执行一次。部分成交后撤销仍保留已经成交的部分。模拟券商订单也持久化到提案文件旁的 `simulated_orders.json`，可跨进程恢复。

Activity 展示本地订单、累计成交、券商状态、最近同步时间及错误。券商连接失败时仍能显示本地记录，并明确标记数据不完整。未解决的订单会阻止同一交易账户继续提交新订单。

以下情况保留为需要人工核对，不能盲目重试：提交结果不明且券商暂时查不到订单、券商累计成交倒退、订单身份不一致、只有均价变化而没有新增成交、升级前已经执行但没有成交游标的旧订单。先在券商侧核对，再制定账本修复方案；不要删除提案或游标来绕过阻塞。

## 事务存储、迁移与备份

提案、不可变审批凭证、订单、成交、资金/持仓预留、回撤阶梯和两个组合账本的权威状态都在 `state/trading_state.sqlite3`。提交券商前，订单意图和账户预留在一个短事务中提交；券商网络请求期间不持有数据库事务。一个账户只能存在一张未解决订单，因此两个进程也不能重复占用同一笔现金。订单结束后自动释放预留。

现有 `proposals.json`、`fills.jsonl`、回撤阶梯 JSON 和两个 portfolio YAML 是一次性迁移来源。先停掉 API 和恢复器，再执行：

```bash
uv run ct-state migrate
uv run ct-state status
uv run ct-state backup
```

迁移不会删除旧文件；迁移后程序优先读取 SQLite。备份写到 `state/backups/`，使用 SQLite 在线备份接口获得一致快照。部署后应每天备份，并把备份复制到加密的第二位置。不要用 Finder 拷贝一个正在写入的 `.sqlite3` 文件，也不要把活跃数据库放在网络盘或同步盘。恢复前先停服务，保留现场数据库，再用整份备份替换。

这套方案面向单机、单写入主机。它解决并发覆盖、现金重复占用和多文件半写入，不提供跨机器高可用。完整的券商成交更正仍需要人工核对流程。

## 行情、证据与产品结构

新开仓要求可验证的研究价格、日期、来源、采集时间和配置要求的分析师报告；存在未解决的重要信息时直接拒绝。执行报价必须携带券商给出的、带时区的市场时间；本机收包时间不能替代。缺失时间、超过 120 秒、未来时间、无效或交叉买卖盘，以及价差超过 0.5% 都会阻止提交。新开仓还要求有效的研究参考价，不能把旧提案按现价重新定价后执行。

ETF 必须属于配置中的明确标的池。杠杆、反向、单一股票、加密资产、商品期货及备兑看涨结构会被确定性排除；身份不明的 ETF 不会被当成普通 ETF。Sandbox 的开仓同时受 Sandbox 自身和总组合回撤阶梯约束，总组合进入 WARNING 后也不能继续加 Sandbox 风险。

## 研究任务恢复

研究请求保存在同一个数据库。相同日期、标的、桶和产品类型的活跃请求只保留一个；默认最多并行两个，单次最长 90 分钟，异常退出最多用同一个 run ID 和上游 checkpoint 恢复一次。API 重启后，仍存活的 worker 继续运行；已退出但没有结果的任务重新排队。状态由 worker 的退出码和 `decision_record.json` 决定，不再根据日志里出现的单词猜测。

研究页每 10 秒读取持久队列。电脑或手机刷新页面后会自动接回 QUEUED/RUNNING 的任务。`GET /research/jobs` 查看队列，`GET /research/{run_key}` 查看结构化状态和日志尾部。

## 前端与验证

真实模式先读取接口，没有数据时不填充示例值。每个接口独立记录成功时间和错误，过期阈值为其轮询间隔的两倍。`?demo=1` 为显式示例模式，不发送接口请求，也不能操作账户。

研究文本、风控理由、日志提示和 HTML 属性值统一转义；同源链接校验拒绝脚本链接；控制台 CSP 禁止内联脚本。页面脚本已提取到 `ui/assets/pages/`。

验证命令：

```bash
uv run pytest -q
node --test tests/frontend.test.cjs
```

测试覆盖卖出/减仓、部分与延迟成交、提交后断网、进程重启、记账中断重放、并发审批、会话与 CSRF、示例数据隔离、HTML 注入、审批对象变更和重复点击。所有执行测试使用临时状态和模拟券商，不连接真实交易账户。

`deploy/checks.sh` 一次跑完 Ruff、pytest、前端用例和密钥扫描，是发布前的统一入口。

## 已登录设备

「更多 → 设备与通知」页列出每一台登录中的设备：设备标识（如 `iPhone · Safari`，由浏览器 User-Agent 推断，**只用于显示**，不参与任何判断）、最近使用时间、剩余天数，当前设备会被标出。每台可以单独退出，也可以一次退出除当前设备外的全部。丢手机不再需要改密码把电脑一起踢下线。

命令行同样可查：

```bash
uv run ct-state sessions
```

输出包含会话 ID、设备、创建/最近使用/到期时间和剩余天数，**不包含令牌**。控制台通过一个不透明的会话 ID 撤销；令牌哈希始终留在数据库里，所以"看到设备列表"永远无法转化成"冒充某台设备"。

**使用会记录时间，但不会延长期限。** 30 天从登录那一刻算起：一个一直开着轮询的浏览器标签页不会让会话永久有效。到期即失效，并从列表中消失。

设备标识和会话 ID 两列是后加的。旧版本写入的数据库没有这两列，升级时会就地补上，**已有登录不会被清掉**；那些会话在下一次被使用时才拿到 ID，在此之前列表里显示为"(assigned on next use)"，也还不能单独撤销。

## 定时研究：什么时候真的会跑

操作系统的调度器只决定命令什么时候被调用；这次调用要不要做事，全部由 `risk_profile.research_schedule` 决定，因此手动触发、定时触发、重启后的补跑得到同一个答案：

- **节假日与周末**：按交易日历回退到最近一个已收盘交易日，或按 `on_non_session_day: skip` 直接跳过。不依赖手工维护的假期表。
- **当天还没收盘**：分析上一个已完成交易日。
- **同一周期已经执行过**：跳过。周期键（如 `weekly:2026-W36`）在启动任何研究之前就被占用，所以重启后再次触发会接上同一个周期，而不是把这一周研究两遍。
- **当日额度用完**：跳过并给出计数。`max_analyses_per_day` 覆盖所有入口，手动研究也计入——订阅额度是同一个池子。
- **系统暂停**：**研究照常进行**。暂停是关于下单的，不是关于分析的；暂停期间产生的提案在执行时仍会被硬性风控挡住。要连研究一起停，把 `run_while_paused` 设为 `false`。
- **已 halt / 额度耗尽 / 配置错误**：跳过，并写明是哪一种。

每次跳过都会记录原因，和"下一次运行时间"一起显示在系统页，所以"周五为什么什么都没跑"可以在手机上回答。

因订阅额度中断的任务会在重置窗口之后自动重新排队，最多 `max_limit_recoveries` 次。跑偏的任务可以在研究页停止，否则它会一直占着并发名额直到超时。

## 手机通知（PWA + 原生推送）

控制台可以"添加到主屏幕"变成一个 App，并接收 iOS 原生通知。这条路和微信/企业微信转发最大的
区别是**没有中间人能读到内容**：推送内容用手机自己生成的密钥加密，苹果只负责投递一个它打不开的
信封。也不需要注册任何第三方账号。

手机上（需要 iOS 16.4+）：

1. Safari 打开控制台 → 分享 → **添加到主屏幕**
2. **从主屏幕那个图标打开**（Safari 标签页收不到推送，这是苹果的限制）
3. 更多 → 「设备与通知」→ 「本机通知」→ **开启通知** → 允许
4. 点「发一条测试」确认能收到

服务端只保存订阅端点的哈希和一个设备标签，端点本身不会通过接口回传——**谁拿到端点谁就能向这台
设备推送**，所以它和其他不能外泄的东西一起放在 0600 的状态库里。VAPID 私钥只在本机，永不轮换
（轮换会让所有已订阅设备失联）。

推送走苹果的通道，**不需要 Tailscale**。所以人在外面、VPN 关着也能收到"有提案要审批"，再打开
Tailscale 进去处理。

**Service Worker 只做推送，没有 fetch 处理器，不缓存任何东西。** 两个原因：缓存过的页面会把旧
价格、旧回撤等级、旧提案当成当前状态显示；更要紧的是，能离线的页面会诱导离线操作，而一条离线排队
稍后补发的审批，等于对着一个已经变了的世界授权——时效时钟、执行前复核和第二次硬性风控存在的意义
就是挡住这件事。所以审批路径永远不离开网络。

**仍然解决不了"Mac 挂了"**：死掉的机器发不出任何东西。那个只能靠外部心跳。

## 通知与离线监测

`notifications.channel` 默认为 `none`：事件仍然会被收集、去重和记录（`ct-notify status` 可查），但**不会发送任何消息**。选择渠道并提供凭据，才是授权发送这件事本身，这个决定不在代码里做。

消息只说明发生了什么、该打开哪个页面，不携带凭据、账号或报价——它要经过不属于本系统的基础设施。持续存在的情况（未审批的提案、失效的凭据）每 `min_interval_seconds` 最多提醒一次；失败的端点按退避重试，达到上限后放弃。

在这台 Mac 上运行的任何东西都无法报告"这台 Mac 没了"。把 `CT_HEARTBEAT_URL` 指向一个期待定期心跳、缺失即告警的外部服务，这是断电或断网能传到手机的唯一路径。

## 后台任务与磁盘

每个后台活动都会记录最近一次成功的时间，系统页把它和预期间隔对比。**从未运行过也算超时**——一个从来没被加载的任务，和一个健康但空闲的任务，在需要它之前看起来完全一样。

`maintenance` 每天轮转 launchd 日志（否则会无限追加）、清理超过保留期的运行产物报告正文（保留每一份 `decision_record.json`），并在剩余磁盘低于阈值时以非零退出码结束。

## 恢复演练

恢复从来不只是拷贝文件：

```bash
uv run ct-state restore --source <backup.sqlite3[.enc]> --into <目录> [--key-file <文件>]
```

它会拒绝损坏的快照，撤销快照里的全部控制台会话（它们在快照那一刻有效，不代表现在有效），释放过期的订单预留，并列出真实状态只有券商知道的订单。在允许继续执行之前，先到券商侧核对这些订单，并记录数据丢失窗口：备份时间点之后的一切都没有了。

状态键现在相对于数据库所在目录保存，所以备份可以恢复到另一个目录或另一台机器上，账本、提案和证据仍然彼此关联。旧的绝对路径键会在数据库第一次被打开时自动改写。

## 资金与收益口径

入金不是收益。每个账户分别报告"净入金"（初始配额 + 已登记的出入金）与"投资损益"（权益 − 净入金），收益率按净入金计算。登记一笔入金：

```bash
uv run ct-state cashflow --bucket core --amount 500 --kind deposit
```

概念组合（核心 + 沙盒）与微实盘账户各有自己的账本和历史高点，因此不能把两者相加后去和任何一个高点比较。组合页确实显示合计数时，会在同一行说明它跨越了两种性质的资金。

## 这套东西到底有没有用

测试通过证明的是软件行为正确，不能证明多 Agent 研究值这个成本——任何工程证据都不能。只有一个**事先声明、持续记录**的样本可以回答。

```bash
uv run ct-evaluate start --note "为什么开这次研究"   # 只做一次，同时冻结规则
uv run ct-evaluate snapshot                          # 每天；维护任务会自动做
uv run ct-evaluate report                            # 随时
uv run ct-evaluate stop --reason "..."               # 结束；报告要留着
```

三点让这份记录值得读：

**规则事先冻结。** 纸面资金、标的范围、调度、风险配置和模型设置在研究开始时被指纹化，之后每份报告都会说明指纹有没有变过。看到结果再定规则，正是把一个策略"讲得好看"的办法；规则中途变了，报告会明说样本不同质，而不是悄悄平均掉。

**统计"没做什么"。** NO_TRADE、被拒绝和过期的提案、失败的任务、因订阅额度中断的任务、以及在证据不完整情况下得出结论的比例，全部进入报告。只记录成交等于只记录"这套系统选择动手的那些时刻"，那是它对自己判断的有偏采样。

**收益剔除入金。** 策略和基准都换算成一个跨现金流连续的单位净值，所以入金不会变成收益，**在水下追加的入金也不会修复回撤**。基准在研究起始日一次买入并持有，并在相同日期按当天价格接受相同入金——这才让两边的收益可比。

报告同时给出成本：模型调用次数、研究耗时、从提案出现到人做决定的中位分钟数、换手，以及相对分析用价的实际滑点（基点）。`observation_days` 是"这份记录开始值得读"的天数，`minimum_days_for_judgement` 是"它能支撑一个判断"的天数；没到之前，每份报告都会在正文里说出来。

停止规则写在 `evaluation.stop_rules`，触发时会在报告里列出，但**不会自动停止任何东西**——停不停是人的决定，事先声明阈值的意义就是让这个决定在亏损有机会替自己辩解之前就做好。
